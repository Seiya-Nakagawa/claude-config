# リリースフロー・CI/CD 監視（手順詳細）

[git-workflow.md](../../rules/git-workflow.md) 9章・12章の原則に基づく手順の詳細。
原則（動作確認前に CI を起動しない、マージは承認制、本番へのローカルデプロイ禁止）は
git-workflow.md を正とする。

## 1. CI/CD 監視・承認フロー

PR 作成後、当該リポジトリに CI（ビルド・テスト・Terraform 等 IaC の plan 実行等）が設定されている
場合は、以下の流れに従う。ユーザーの「CI 完了しました」等の報告を待たず、AI が自ら監視・確認まで
一気通貫で行う。リポジトリに CI が設定されていない場合は、本章の監視フローは適用しない
（ただしマージ前のユーザー承認は [git-workflow.md](../../rules/git-workflow.md) 12章に従い必須とする）。
PR 作成に至るまでの流れ（デプロイ・動作確認）は[git-workflow.md](../../rules/git-workflow.md) 12章に従う。

### 1.1. CI 実行の監視

- PR 作成後、CI の実行を待たず放置しない。`gh pr checks {PR番号} --watch` や `gh run watch` 等で
  完了まで監視する
- CI の実行 URL を取得し、必ずテキストメッセージでユーザーに提示する（コマンド出力に埋もれさせない）

### 1.2. 結果の抽出・提示

- CI のログ全文をそのまま貼り付けず、意味のある要約を抽出して提示する
  - IaC の plan の場合: 追加・変更・削除の件数サマリーと、変更されるリソースの一覧を提示する。
    さらに `+`/`-`/`~` の属性単位の差分を照合し、今回のコード変更で意図した属性のみが変化しているかを
    検証する。コード変更前から実態とコードがズレていたドリフト等、意図しない変更が含まれる場合は
    見落とさず必ずユーザーに明示する
  - テスト・ビルドの場合: 成功・失敗件数、失敗時は失敗内容と原因箇所
- 詳細な確認が必要な場合は、ログをファイルに保存し Read ツールで読む（コンテキスト節約のため、
  長大なログをそのまま出力しない）

### 1.3. 承認と実行

- CI 結果の提示後、マージ・本番適用（apply/deploy）等のさらなる不可逆操作は、
  ユーザーから明示的な承認を得てから AI が実行する（[git-workflow.md](../../rules/git-workflow.md) 1章の原則に従う）
- 承認を得たら、AI がマージを直接実行する

  ```bash
  gh pr merge {PR番号} --squash --delete-branch
  ```

  `--delete-branch` により、`main` への切替・pull・ローカルブランチ削除・リモートブランチ削除が
  自動実行される

- マージ後に自動で本番反映（apply/deploy）が走る CI/CD 構成の場合、AI はその CI の完了も同様に
  監視し、結果をユーザーに報告する。ユーザーが別途 URL を確認しに行く必要がないようにする

## 2. リリース方針（標準フロー）

全リポジトリ共通のリリースの流れ。**「先にデプロイ先環境で動作確認を済ませ、確認済みのコード変更のみを
コミット・プッシュして PR・CI・CD に流す」** ことを原則とする。

### 2.1. 標準フロー

| 手順 | 内容 | 担当 |
| --- | --- | --- |
| 1 | コード修正 | AI |
| 2 | ローカルまたはステージング環境へデプロイ（2.2節） | AI |
| 3 | デプロイした環境での動作確認 | AI |
| 4 | 動作確認の結果をユーザーに報告する。ユーザー自身の確認が必要な対象（GAS 等）は、依頼して確認完了を待つ | AI → ユーザー |
| 5 | 動作確認の完了後、コミット・プッシュ・PR 作成を行う（ユーザーの許可は不要）。PR オープンをトリガーに GitHub Actions で CI、またはドライランを実行する（ドライランが可能なデプロイ対象の場合） | AI |
| 6 | CI の結果に問題がなければ、結果を提示し**マージの許可を得る** | AI → ユーザー |
| 7 | **ユーザーの許可を得たらマージ**し、マージをトリガーに GitHub Actions で CD を実行する。CD の結果を監視して報告する | AI |

- 動作確認前は、CI の起動契機となるコード変更をコミット・プッシュしない
  （ドキュメントのみの変更等は、動作確認を待たずに PR にしてよい）
- ユーザーの許可が必要なのは手順6のマージのみである（ユーザー自身の確認が必要な対象の動作確認を除く）
- 手順5以降の CI の監視・結果提示・マージ・CD の監視の詳細は、1章に従う
- CI で問題が検出された場合、または追加の修正が必要になった場合は手順1へ戻る。
  デプロイ済みの挙動に影響する修正を加えたときは、手順2〜4（再デプロイ・再確認）をやり直す

### 2.2. プロジェクトごとの違い

手順2のデプロイ先、手順5の CI / ドライランの有無、手順7の CD の有無はプロジェクト・対象により異なる。
具体的な値は各リポジトリの `CLAUDE.md` に従い、以下を基準とする。

| 対象 | 手順2 のデプロイ先 | 手順5 の CI | 手順7 の CD |
| --- | --- | --- | --- |
| Terraform（ステージング環境あり） | ステージングへ `plan` / `apply` | `plan`（ドライラン） | 本番へ `apply` |
| Terraform（環境が単一で CI/CD あり） | なし（ステージングが無いため、事前の動作確認は PR 上の `plan` 差分確認に限る。[terraform.md](../../rules/terraform.md) 6章） | `plan`（ドライラン） | 本番へ `apply` |
| Terraform（環境が単一で CI/CD なし） | 対象環境へ `plan` / `apply`（[terraform.md](../../rules/terraform.md) 6章） | なし | なし |
| Lambda | 検証環境の関数コードを更新 | テスト・ビルド | 本番の関数コードを更新 |
| GAS | 既存デプロイを更新（[gas-deploy-flow.md](../../rules/gas-deploy-flow.md)）。CI/CD で自動デプロイするスクリプトは gas-deploy-flow.md 5章に従い、事前デプロイなし | 設定がある場合のみ | 設定がある場合のみ（gas-deploy-flow.md 5章） |
| ドキュメントのみ | なし（手順2〜4を省略） | 設定がある場合のみ | なし |

- CI / CD が存在しない対象では、手順5の CI 監視・手順7の CD 監視を省略する。
  ただし手順6のマージ承認は必須とする
- 本番環境へのデプロイは、常にマージ後の CD で行う。ローカルから本番へ直接デプロイしない
