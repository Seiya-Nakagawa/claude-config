# ドキュメント体系規約

全リポジトリ共通の設計文書の体系・フォルダ構成・章立てを定義する。
**「何を実現するか（What）」と「どう実現するか（How）」を文書レベルで分離する。**

本規約はプロジェクトごとの揺れを排除することを目的とする。
フォルダ名・ファイル名・章立ては**本規約の定義をそのまま使用し、独自に変更しない**。

## 0. 適用範囲

**全てのプロジェクト（リポジトリ）で、規模の大小を問わず要件定義書・基本設計書を必ず作成する。**
ドキュメント作成が作業依頼に明示的に含まれていない場合でも、対象プロジェクトに
要件定義書・基本設計書が未整備であれば、本規約に従って作成する。

**例外**: AI エージェントの設定・規約そのものを管理するリポジトリ（`~/.claude/` を管理する
`claude-config` 等）は、要件定義書・基本設計書を作成せず `README.md` のみとする。
規約ファイル自体が仕様であり、別途設計文書を持つと二重管理になるため。

### 0.1. プロジェクト種別

基本設計書の構成は、プロジェクトを以下の2種別に分けて定める。
種別は「そのリポジトリが管理する主たる対象」で判定する。

| 種別 | 定義 | 基本設計書の構成 |
| ---- | ---- | ---- |
| インフラ管理プロジェクト | クラウドリソース・サーバ・ミドルウェア等の基盤を IaC（Terraform・Ansible 等）で管理するリポジトリ | **分野ごとの章立て分割を必須とする**（1.3節）。`DESIGN.md` は作成しない |
| アプリケーションプロジェクト | 業務アプリ・関数アプリ・GAS・ライブラリ等のアプリケーションコードを管理するリポジトリ | `DESIGN.md` 1ファイルとする（3.2.1節） |

- インフラとアプリの双方を含むリポジトリはインフラ管理プロジェクトとして扱い、アプリ部分は
  コンポーネント単位の設計書（1.4節）として `02.design/90.components/` に置く
- 要件定義書（`REQUIREMENTS.md`）・詳細設計書・構築手順書の構成は種別によらず共通とする

## 1. フォルダ構成

```text
docs/
├── 01.requirements/           # 要件定義
│   ├── REQUIREMENTS.md
│   ├── {対象}要件定義書.md      # コンポーネント単位の場合のみ（1.4節）
│   └── old/                   # 旧世代の要件定義書
├── 02.design/                 # 基本設計
│   ├── DESIGN.md              # アプリケーションプロジェクトのみ
│   ├── {NN}.{英名}/           # インフラ管理プロジェクトの章ディレクトリ（1.3節）
│   │   └── {章番号}章_基本設計書_{章タイトル}.md
│   ├── 90.components/         # コンポーネント単位の設計書のみ（1.4節）
│   │   └── {対象}設計書.md
│   ├── 99.appendix/           # 別紙（図面）・一覧・台帳（1.3節）
│   └── old/                   # 旧世代の設計書
├── 03.detailed-design/        # 詳細設計（作成する場合のみ）
│   └── {対象}詳細設計書.md
├── 04.build/                  # 構築（初期構築の手順書）
│   └── {NN}_{内容}.md
└── 05.operations/             # 保守・運用（Git 管理しないプロジェクトのみ）
    └── {NN}_{内容}.md
```

- **フォルダ名は数字と英語のみで構成する**（1.1節）。文書のファイル名は日本語でよい
- **構築手順書は `04.build/` に格納する**。環境の初期構築や再構築のときに実行する手順、および
  構築した環境を利用するための手順（接続手順等）を対象とする（2.4節）
- **保守・運用のフォルダ（`05.operations/`）は、Git 管理しないプロジェクトのみ作成する**。
  Git 管理するプロジェクトでは、保守・運用の作業を GitHub Issue で管理し、手順や結果は
  Issue に記録するため、フォルダを設けない（2.4節）
- **詳細設計書は、設定値・パラメータ・内部構造のレベルの設計が必要な場合に作成する**。作成する場合のみ
  `03.detailed-design/` を設ける（1.4節・2.3節）
- 要件定義書・基本設計書は `01.requirements/` `02.design/` に格納し、`docs/` 直下には置かない
- フォルダの採番は文書の作成順（要件定義 → 基本設計 → 詳細設計 → 構築 → 運用）とし、
  番号が重複しないようにする。GitHub Milestone（[git-workflow.md](git-workflow.md) 8章）の番号とは
  対応させない。対応するフェーズは、要件定義（`01`）、基本設計（`02`）、
  構築（`03`・`04`。詳細設計書と構築手順書）

作業証跡ログ（`*.log`）は Git 管理外とし、本ディレクトリには置かない。保存先・命名規則は
[ssh-operations スキル](../skills/ssh-operations/SKILL.md) に従う。

### 1.1. 命名規則

| 対象 | 規則 |
| ---- | ---- |
| 階層ディレクトリ | `NN.英名` 形式（半角数字2桁 + 半角ピリオド + 英小文字）。単語の区切りはハイフン（例: `03.detailed-design`）。**日本語・アンダースコア・空白を使わない** |
| 要件定義書 | `REQUIREMENTS.md` に固定 |
| 基本設計書 | `DESIGN.md` に固定 |
| 分割した要件定義書 | `{対象}要件定義書.md`（例: `決済連携バッチ要件定義書.md`） |
| コンポーネント単位の設計書 | `90.components/{対象}設計書.md`（例: `MySQL設計書.md`、`Kubernetes設計書.md`） |
| 詳細設計書 | `{対象}詳細設計書.md` |
| 手順書 | `{NN}_{内容}.md`（半角数字2桁の連番 + `_` + 内容）。連番はフォルダごとに `01` から振る。構築手順書は Issue ごとに1ファイルとし、着手順に採番する。Issue 番号はファイル名に含めず文書内の「概要」に記載する |

ディレクトリ名のみ英語に統一するのは、パスに日本語・記号（`・` 等）が混在すると URL
エンコードやシェル操作で扱いが煩雑になるため。文書のファイル名は一覧性を優先して日本語を許容する。

### 1.2. ディレクトリ作成の要否

| 対象 | 作成条件 |
| ---- | -------- |
| `01.requirements/` | **必ず作成する**（`REQUIREMENTS.md`、および1.4節のコンポーネント単位要件定義書の格納先） |
| `02.design/` | **必ず作成する**（`DESIGN.md`、または1.3節の章立て分割文書の格納先） |
| `04.build/` | **構築フェーズ（Milestone「03.構築」）の Issue でコードを変更する場合は必ず作成する**（[docs-sync.md](docs-sync.md) 4章参照） |
| `02.design/{NN}.{英名}/` | **インフラ管理プロジェクトでは必ず作成する**（1.3節）。アプリケーションプロジェクトでは `DESIGN.md` 1ファイルでは扱いきれない場合のみ |
| `02.design/90.components/` | コンポーネント単位の設計書を作成する場合のみ（1.4節） |
| `02.design/99.appendix/` | 別紙（図面）、または一覧・台帳を作成する場合のみ（1.3節） |
| `05.operations/` | Git 管理しないプロジェクトで、運用手順書を作成する場合のみ。Git 管理するプロジェクトでは作成しない。作業証跡ログ（`*.log`）は Git 管理外のため対象外 |
| `03.detailed-design/` | 詳細設計書（設定値・パラメータ・内部構造レベルの設計書）を作成する場合のみ設ける（1.4節・2.3節）。作らない場合は空ディレクトリを置かない |
| `old/` | 旧世代の文書が発生した場合のみ（第4章参照） |

### 1.3. 章立てによる分割（インフラ管理プロジェクトは必須）

**インフラ管理プロジェクトでは、`02.design/` 配下を分野ごとの章ディレクトリに必ず分割する。**
アプリケーションプロジェクトでは `DESIGN.md` 1ファイルを基本とし、対象範囲が広く1ファイルでは
扱いきれない場合に限り分割してよい。分割する場合の構成・命名は以下に固定する。

```text
docs/
└── 02.design/
    ├── {NN}.{英名}/
    │   └── {章番号}章_基本設計書_{章タイトル}.md
    ├── 90.components/         # コンポーネント単位の設計書（1.4節）
    └── 99.appendix/           # 別紙（図面）・一覧・台帳
        ├── 別紙_{タイトル}.drawio.svg
        └── {タイトル}.md
```

| 対象 | 規則 |
| ---- | ---- |
| 章ディレクトリ | `{NN}.{英名}`（1.1節に従い数字2桁 + 英名。例: `01.system-architecture`） |
| 章ごとの設計書 | `{章番号}章_基本設計書_{章タイトル}.md`（章番号はゼロ埋めしない） |
| 図面（別紙） | `99.appendix/別紙_{タイトル}.drawio.svg`（章ディレクトリには置かない） |
| 一覧・台帳 | `99.appendix/{タイトル}.md` |

- ディレクトリ名の章番号はゼロ埋めし（`01.`）、ファイル名の章番号はゼロ埋めしない（`1章_`）。
  ディレクトリは並び順を揃える必要があるため、ファイル名は本文中の章番号表記と揃えるため
- **章番号は `1` から欠番のない連番とする**。章の削除・統合で欠番が生じた場合は、後続の章の
  ディレクトリ名・ファイル名・文書内の章番号・他文書からの参照を繰り上げて詰める
- `90` 番は章ディレクトリ（`01`〜）と `99.appendix/` の間に並べるための予約番号であり、章には使わない
- 章立てに分割した場合、`DESIGN.md` は作成せず、章ごとの設計書の総体を基本設計書とみなす
- **別紙（図面）および一覧・台帳系ドキュメント（監視項目一覧等）は、章ディレクトリの外に置く
  `99.appendix/` に集約する**。特定の章に属する図面であっても章ディレクトリには置かず、
  各章の設計書から相対リンクで参照する（図面が複数章から参照されるため、所在を1か所に固定する）
- 章の分け方と章ディレクトリの英名は1.3.1節のカタログに従う。実際に採用した章は
  `02.design/` 配下のディレクトリ構成が正であり、プロジェクト個別の `CLAUDE.md` には記載しない
- アプリケーションプロジェクトが分割する場合は、1.3.1節のカタログではなく
  3.2.1節の標準章立てを分割して各章に割り当てる

#### 1.3.1. インフラ管理プロジェクトの標準章カタログ

章ディレクトリの英名・章タイトルは以下のカタログから選び、独自の名称を作らない。
**プロジェクトに該当する章のみを採用し、カタログの並び順を保ったまま `1` から欠番なく
振り直す。** 章ごとにディレクトリと文書を持つ構成のため、内容のない章は作らない
（第3章の「該当がない章は『該当なし』と明記する」は、章立て分割時の章の採否には適用しない）。

| カタログ番号 | 章ディレクトリの英名 | 章タイトル | 扱う内容 |
| --- | --- | --- | --- |
| 1 | `system-architecture` | システム構成 | 設計方針、全体構成図、環境一覧、技術スタック |
| 2 | `network` | ネットワーク設計 | ネットワーク空間・サブネット構成、通信フロー、DNS |
| 3 | `server` | サーバ構成 | サーバ・データベース等のインスタンス構成と採用方式 |
| 4 | `performance` | 性能・拡張 | サイジング、スケーリング方式、ストレージ |
| 5 | `availability` | 耐障害性 | 冗長化方式、可用性ゾーン配置、単一障害点 |
| 6 | `security` | セキュリティ設計 | 境界防御、暗号化、認証・認可、脆弱性対策 |
| 7 | `account` | アカウント管理 | 利用者・権限の管理方式、特権の取り扱い |
| 8 | `platform-control` | 基盤制御 | 基盤の操作経路・自動化・IaC の実行方式 |
| 9 | `job` | ジョブ管理 | 定期実行ジョブの方式、スケジュール、実行結果の管理 |
| 10 | `monitoring` | 監視・ログ設計 | 監視方式、メトリクス・ログの収集と通知 |
| 11 | `backup` | バックアップ・リストア設計 | 取得方式、保管先、世代、RTO / RPO |
| 12 | `release` | リリース方式 | リリース単位、適用手順、切り戻し |
| 13 | `lifecycle` | ライフサイクル管理方式 | パッチ・バージョン・EOL 対応、証明書更新 |
| 14 | `mail` | メール設計 | メール送受信の経路、送信ドメイン認証 |

- カタログ番号は並び順の基準にすぎない。ディレクトリ名・ファイル名・文書内で使う章番号は、
  **採用した章を `1` から振り直した連番**とする
- カタログにない観点が必要な場合のみ章を追加し、カタログの最後（14 の後）に並べる
- 対象範囲の拡大により章を追加する場合も、カタログの並び順に従う位置へ挿入し、
  後続の章番号を振り直す（1.3節の連番ルール）

### 1.4. コンポーネント単位の文書

システム全体ではなく特定のコンポーネント（関数アプリ、バッチ、外部連携、ミドルウェア等）を
対象とする要件定義書・設計書も、**`docs/01.requirements/` `docs/02.design/` に集約する**。
コンポーネントのソース配下（`lambda/docs/`、`{アプリ名}/docs/` 等）に置かない。

| 対象 | 格納場所・命名 |
| ---- | ---- |
| コンポーネントの要件定義書 | `docs/01.requirements/{対象}要件定義書.md` |
| コンポーネントの設計書 | `docs/02.design/90.components/{対象}設計書.md` |
| コンポーネントの詳細設計書 | `docs/03.detailed-design/{対象}詳細設計書.md` |

- **基本設計と詳細設計の振り分け**: コンポーネントの責務・構成・外部インタフェース・採用方式を書いた
  文書は設計書（`90.components/`）、設定値・パラメータ・ディレクトリ構成・内部構造を書いた文書は
  詳細設計書（`03.detailed-design/`）に格納する。`90.components/` と `03.detailed-design/` に
  同じ対象の文書を置く場合は、記載を重複させずリンクで参照する
- コンポーネント単位の設計書は、章立て分割（1.3節）の有無にかかわらず `02.design/90.components/`
  に格納する。`DESIGN.md`・章ディレクトリと同じ階層に直接置かない（システム全体の設計と
  コンポーネントの設計を分けて見通しを保つため）
- コンポーネント単位の要件定義書は、`01.requirements/` 直下に置く（章ディレクトリを持たないため）
- 1行目のタイトルはファイル名（拡張子を除く）と一致させる
- **README はソース配下に置いてよい**。コンポーネントの使い方・トリガー・環境変数・依存関係を
  書いた `README.md` は対象外とし、設計文書のみを `docs/` に集約する

**理由**: 文書がソースツリーに散在すると、文書の全体像が把握できず、フェーズ間の整合
（要件 → 設計 → 構築）も追えなくなる。文書の所在は `docs/` 配下に一元化する。

## 2. 各文書のスコープ

### 2.1. 要件定義書（What）

**利用者・発注者の視点で「何を実現するか」を書く。実現手段は書かない。**

記載する。

- プロジェクトの目的・背景
- 対象範囲（スコープ内 / スコープ外）
- 用語定義
- 機能要件（利用者視点で「何ができるか」）
- 非機能要件（可用性・性能・セキュリティ・運用・コストの**目標値**）
- 制約・前提条件（既存基盤、採用が決定済みの言語・プラットフォーム等）

記載しない（基本設計へ送る）。

- システム構成図、コンポーネント配置
- ライブラリ・パッケージの選定とバージョン
- テーブル定義、カラム、データ型、文字コード
- 画面レイアウト、画面遷移
- API のエンドポイント、リクエスト / レスポンス形式
- アルゴリズム、判定ロジックの具体的な条件式

> **判断基準**: その記述を消しても「システムが満たすべき条件」が変わらないなら、それは設計である。

### 2.2. 基本設計書（How / 外部設計）

**要件を満たすための構造と、外部から見える振る舞いを書く。**

- システム構成図、コンポーネントの責務と配置
- 技術スタック（ライブラリ名と**バージョンを確定させる**）
- データモデル（ER 図、テーブル定義、型、制約、文字コード）
- 画面一覧、画面遷移図、主要な画面項目
- 外部インタフェース（API 仕様、連携先、バッチの起動方式）
- 非機能要件の実現方式（認証方式、バックアップ手順、監視方法）

### 2.3. 詳細設計書（How / 内部設計）

**実装者が迷わない粒度で内部構造を書く。規模が小さく、基本設計書で足りる場合は作成しなくてよい。**

- モジュール / クラス構成と責務
- 処理フロー、シーケンス図
- アルゴリズム、バリデーション仕様
- エラーハンドリングの方針

OS・ミドルウェアなどのインフラ構成要素（Ansible で構成するもの等）では、上記に代えて次を書く。

- 設定ファイル・パラメータの値と、その値にした理由
- ディレクトリ・ユーザー・権限の構成
- セキュリティ設定、ログ・監視・バックアップ設定の具体内容

### 2.4. 構築手順書（How / 実施手順）

**構築フェーズで Issue ごとに実施した（する）作業手順を、再現可能な粒度で書く。**
他の設計文書と異なり内容を確定事項に限定せず、実施したコマンドや設定変更などの
手順そのものを時系列・工程順に記載する（第5章の「プロセス情報を書かない」は本文書には適用しない）。
構築フェーズ（Milestone「03.構築」）の Issue でコードを変更する場合は必ず作成し、
`docs/04.build/` に格納する（[docs-sync.md](docs-sync.md) 4章参照）。

記載する。

- 目次（`##`/`###` 見出し全件へのアンカーリンク。手順が長くなりやすいため、
  一覧から該当手順へ移動できるようにする。第5章の目次生成ルールに従う）
- 対応する Issue 番号と概要
- 前提条件（事前に必要な環境・ツール・認証情報の準備状況）
- 構築作業そのもののコマンド・設定変更内容を番号順に記載
- コマンドが何を実施しているかの説明。コード ブロック直下に、コマンドの実行順と
  対応させた箇条書きで説明のみを記載する（コマンド文字列自体はコードブロックに
  既出のため再掲しない）。ただし `cd` / `ls` / `mkdir` / `rm` など、用途が名前から
  自明な汎用 Linux コマンドは説明を省略してよい
- 複数の操作を `sh -c '...'` や `&&` 等でワンライナーにまとめず、実際に1つずつ
  実行する手順として分割する。特にコンテナへのログインのように別シェル・別環境に
  入る操作を含む場合は、「ログインする」「（ログイン後のシェルで）実行する」を
  別のコマンド・別のコードブロックに分ける

記載しない。

- Git 操作（ブランチ作成、コミット、push、PR 作成等）。[git-workflow.md](git-workflow.md) の
  標準フローに従うため、手順書には書かない
- 設計書側への反映作業。[docs-sync.md](docs-sync.md) に従いコードと同一 PR 内で実施するが、
  その作業手順自体は書かない
- 要件定義書・基本設計書・詳細設計書に記載済みの内容の再掲（リンクで参照する）
- 設計書に明記がなく実装時に判断した事項の考察・確認事項。手順書は「何をしたか」のみを書き、
  判断の妥当性の検討は書かない

構築手順書は**「その手順どおりに実行すれば、ゼロから同じ環境を再構築できる」状態を保つ**。
実施後に手順の不足・誤りが判明した場合、または実装の変更に伴い手順が変わった場合は、
**手順書を更新して常に再構築可能な状態に保つ**。更新にあたっては以下を守る。

- **不足していた手順は、再構築時に実行すべき位置へ差し込む。**
  末尾に「追加対応」「補足」等として追記しない
- **実施経緯を書かない。** 「当初は〜だったが」「〜が判明したため追加した」といった
  変更の経緯・理由・時系列は残さず、確定した手順のみを記載する
- 手順の削除・差し替えも同様に、経緯を残さず現行の手順に置き換える

最新のシステム構成は基本設計書側を正とする。

#### 運用手順書

**Git 管理しないプロジェクトに限り**、稼働後に繰り返し実行する運用作業（定期作業、障害対応等）の
手順を `docs/05.operations/` に格納する。Git 管理するプロジェクトでは、保守・運用の作業を
GitHub Issue で管理し、手順や結果は Issue に記録するため、運用手順書のフォルダは作成しない
（構築した環境を利用するための接続手順等は、構築手順書として `04.build/` に置く）。

記載の粒度・書き方（再現可能な粒度、経緯を書かない）は構築手順書と同じ扱いとする。
同じ内容を構築手順書と運用手順書の双方に書かない。初期構築時にのみ実行する作業は
`04.build/` に置き、運用手順書からはリンクで参照する。

## 3. 標準章立て

以下の章立てをそのまま使用する。該当がない章は削除せず「該当なし」と明記する。
プロジェクト固有の章を追加する場合は、標準章の後ろに続ける。
ただし章立て分割を採る基本設計書（3.2.2節）では、章そのものを採否の対象とするため、
採用しなかった章のディレクトリ・文書は作らない（1.3.1節）。

```markdown
### 1.1. 目的
### 1.2. 背景
### 1.3. 方針                    # 既存システムがある場合は移行方針

## 2. 対象範囲

### 2.2. スコープ外
### 2.3. 現行機能との差分          # 既存システムがある場合のみ

## 5. 管理対象データ              # 情報の単位と業務ルール。テーブル定義は書かない
### 5.1. データに関する業務ルール

## 6. 非機能要件
### 6.1. 可用性                   # RTO / RPO
### 6.2. 性能                     # 応答時間、処理件数
### 6.3. セキュリティ

## 7. 制約・前提条件
### 7.1. 採用が決定済みの技術      # 「言語は Python」レベル。ライブラリは書かない
### 7.2. その他の前提
```

### 3.2. 基本設計書

#### 3.2.1. アプリケーションプロジェクト（`DESIGN.md`）

```markdown
## 2. 技術スタック

### 2.2. 採用ライブラリ

## 3. 機能設計                    # 主要機能の実現方式。要件定義の機能要件と対応させる

## 4. データベース設計
### 4.1. 共通方針                 # DBMS、文字コード、照合順序、削除方式
```

#### 3.2.2. 章立て分割時（インフラ管理プロジェクト）

採用する章は1.3.1節のカタログから選ぶ。各章の設計書は以下の形式とする。

- 1行目のタイトルは `# {章番号}章_基本設計書_{章タイトル}` とし、ファイル名と合わせる
- タイトルの直下に `## 目次` セクションを設け、ドキュメント内の見出しへのリンクを記述する
- 見出しレベルは章番号から開始する（4章の場合は `## 4.1`、`## 4.2`、
  サブセクションは `### 4.2.1`、`### 4.2.2`）
- 各章は `{章番号}.1` を「設計方針」とし、その章の設計原則を箇条書きで示したうえで、
  以降の節で構成・方式を記述する
- 章の対象外とする範囲が他章にある場合は「本章のスコープ外」として明記し、
  該当章への相対リンクを張る（同じ内容を複数の章に重複して書かない）
- 要件定義書6章（非機能要件）の各項目は、対応する章（性能 → 性能・拡張、
  可用性 → 耐障害性、バックアップ → バックアップ・リストア設計 等）で実現方式を示す。
  3.2.1節の「7. 非機能要件の実現方式」に相当する章は設けない

## 4. 旧世代文書の扱い

システムを作り直した場合、**旧文書を削除せず** `old/` へ退避する。

1. 旧文書が属する階層ディレクトリ（`01.requirements/`、`02.design/`、`03.detailed-design/` 等）の
   直下に `old/` を作成する
2. 旧文書をファイル名を変えずに `old/` へ移動する
3. 旧文書の冒頭に、後継文書へのリンクと廃止予定を注記する

   ```markdown
   > **注記**: 本ドキュメントは旧{システム構成}版の記録である。
   > 現行の文書は [`../REQUIREMENTS.md`](../REQUIREMENTS.md) を参照すること。
   > {廃止条件}が完了した時点で本ドキュメントは削除する。
   ```

4. 移行が完了し参照不要になった時点で `old/` ごと削除する

## 5. 記述ルール

- 構築手順書の目次（3.4節）は `##`/`###` 見出しをそのままの階層で箇条書きにし、
  各項目を GitHub の見出しアンカー（見出しテキストを小文字化し、記号を除去して
  空白をハイフンに置換したもの。番号の `.` は詰めて連結する。例:
  `### 3.1. uv 環境の初期化` → `#31-uv-環境の初期化`）へのリンクにする。
  `## 1. 概要` から書き始め、目次自身は目次に含めない
- Markdown 記法は [markdown.md](markdown.md) に従う
- 図の記述方式は6章の方針に従う（画像ファイルをそのまま埋め込まない）
- 表を優先し、箇条書きの入れ子を深くしない
- **バージョンは「以降」で濁さず確定値を書く**。範囲指定する場合は上限も明記する
  - 悪い例: `Python 3.12 以降`
  - 良い例: `Python 3.14`、`Python 3.13 以上 3.15 未満`
- 文書には**確定事項のみ**を記載する。検討状況・対応経過・進捗といったプロセス情報は書かない
  （「未記載」「次工程で決定」「〇〇の結果、△△に決定した」等の記述はしない）
- 未決事項・今後検討すべき論点はドキュメントに書かず、**GitHub Issue で管理する**
- 将来的に内容を確定させる必要がある記載箇所は、本文中に `<mark>` タグを付けて示してよい。
  **管理対象の Issue へのリンクを含める**（例: `<mark>通知手段は未確定（[Issue #17](URL)）</mark>`）。
  検討の経緯や状態を説明する文章は書かず、対象箇所と参照先 Issue を示すだけにとどめる
- 他の文書への参照は、文書名や章番号だけのプレーンテキストで済ませず、必ず相対パスの
  Markdown リンクにする（悪い例: `基本設計書 4.2節を参照`。良い例:
  `[基本設計書 4.2節](../02.design/DESIGN.md#42-テーブル定義)を参照`）。
  パスをベタ書きすることも禁止する
- **詳細な設定値は管理しない**: 具体的なパラメータ（CIDR、IP アドレス、リソース名、
  SSL/TLS ポリシー名等）の網羅的な管理は IaC 等のコードや詳細設計書に任せ、基本設計書では
  「なぜその構成にするのか」「どのようなルールで構成するのか」という方針を重視する。
  値そのものを記載すると変更都度の修正が発生するため、方針レベルの記述に留める
- **実装の引用は記載しない**: コードのファイルパス・行番号・リソース名・属性値などの実装引用
  （「実装参照: `terraform/xxx.tf`」など）を本文に記載しない。実装の正は常にコードであり、
  設計書はコードを追跡する責務を持たない
- **経緯・precedent は記載しない**: リソースや設定を追加・削除・変更した場合、設計書には
  変更後の現在の方針・構成のみを記載する。「なぜ削除したか」「以前は〜だったが」
  「これは本リポジトリで初めて〜する事例である」等の経緯・履歴・precedent 的な説明は書かない。
  経緯は git 履歴・PR・Issue に委ねる
- **関心事の分離**: 各章はその章の対象範囲に集中する。OS 内部の設定やアプリケーションレベルの
  論理設計（DB 論理設計等）は、それぞれの専用章または詳細設計で扱う
- **図解の活用**: 文字だけでなく図を積極的に活用し、一目で全体像が理解できるようにする（6章参照）

## 6. 図の作成・管理

### 6.1. Mermaid 図

- ER 図・フローチャート・画面遷移図・シーケンス図等は、原則として Mermaid で記述し、
  画像ファイルを埋め込まない（差分が追えなくなるため）。ただしシステム構成図は
  6.2節に従い drawio で記述する
- **日本語表記**: ラベルやノードの名称は、可能な限り日本語を使用する
- **正式名称**: サービス名やシステム固有の正式名称は英語表記（例: Amazon S3、Cloudflare）を
  許容、または推奨する

### 6.2. drawio ファイル

システム構成図（基本設計書「1.2 構成図」、章立て分割時の全体構成図等、コンポーネント・
ホスト間の配置や依存関係を箱と矢印で示す図）は、**原則 drawio 形式**で記述する。
それ以外の図（ER 図・フローチャート・シーケンス図等）についても、Mermaid で表現しきれない
複雑な図面に限り drawio 形式を使用してよい。

- **拡張子は `.drawio.svg` とする**。draw.io の「編集可能な SVG」形式（SVG の `content` 属性に
  mxfile を埋め込んだ形式）で保存し、draw.io での再編集と GitHub 上での描画の両方を満たす。
  `.drawio`（画像として描画されない形式）・`.png` 等の画像形式では保存しない
- 格納先は `02.design/99.appendix/別紙_{タイトル}.drawio.svg` とする。1.3節の章立て分割を
  採る場合・採らない場合（`DESIGN.md` 1 ファイル構成）のいずれも同様とし、章ディレクトリや
  `DESIGN.md` と同じ階層には図面ファイルを置かない。章立て分割を採らない場合も、
  drawio 図面を作成する時点で `99.appendix/` を作成してよい
- **本文から参照する**: 図を掲載する節に、別紙への Markdown リンクと画像記法
  （`![{図のタイトル}]({相対パス})`）の両方を記載し、本文中で描画されるようにする。
  同じ図を Mermaid でも二重に記載しない
- 環境ごとに構成が異なる場合は、環境ごとのシートに分けて管理し、変更時は全シートの整合性を確認する

### 6.3. 図の更新タイミング

以下の変更を行った場合は、対応する構成図を必ず更新する。

- インフラリソースの追加・変更・削除
- ネットワーク構成の変更
- 環境追加（環境間の構成差分が変わる場合）

## 7. 更新ルール

- コードを変更したら、対応する設計文書を同一 PR 内で更新する（[docs-sync.md](docs-sync.md) 参照）
- 上位文書（要件定義）と下位文書（設計）の内容が矛盾した場合、**上位文書を正**とし、下位を修正する
- 要件そのものが変わった場合は、要件定義書を先に更新してから設計に反映する
