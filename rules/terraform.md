# Terraform 規約

全リポジトリ共通の Terraform 運用規約。
plan / apply / SSH 接続は共通スクリプト（10章）を使う。環境ごとの変数ファイル名、
CI のワークフロー名など、**リポジトリ固有の値はプロジェクト個別の `CLAUDE.md` に従う**。

## 1. 実行担当の分担

- **AI**: ファイル編集、クラウド認証の実行、plan 実行、plan 結果の抽出・提示、
  検証環境・ローカル適用対象環境への apply 実行（ユーザーの承認は不要）、CI/CD 監視・結果確認・ユーザーへの報告
- **ユーザー**: 認証情報（MFA コード等）の提供、マージ承認

## 2. クラウド認証

- Terraform コマンドの実行前に認証状態を確認する
- MFA コードが必要な場合は、ユーザーにテキストでの入力を依頼し、
  受け取ったコードを認証スクリプトの標準入力に渡して認証を完了させる
- 認証情報は 1 セッションあたりの有効期限が切れたら再取得する

## 3. 作業順序（実装・検証）

1. AI: ファイル編集（`*.tf` の修正）
2. AI: 認証確認
3. ユーザー: MFA 要求された場合はコードを入力
4. AI: `plan` を実行する
5. AI: plan 結果から**サマリー（`Plan: X to add, Y to change, Z to destroy`）と変更内容**を
   抽出し、**今回のコード変更で意図した差分以外（ドリフト）が含まれていないか確認する**（3.1節）
6. ドリフトがなければ、`destroy` や置換（`-/+`）を含む場合は対象リソースを明示したうえで
   結果をユーザーに提示し、**ユーザーの承認を待たずに** `apply` を実行する
7. AI: apply 結果（変更されたリソース）をユーザーに報告する
8. AI: 適用先環境での動作確認を行う
9. AI: 動作確認の完了後にコミット・プッシュ・PR 作成を行う（[git-workflow.md](git-workflow.md) 12章。
   PR オープンを契機に CI で `plan`（ドライラン）が実行される）

### 3.1. ドリフト検出時の扱い

plan の差分に、今回のコード変更では説明できない変更（コード変更前から本番実態とコードが
ズレていた属性、手動操作によるドリフト等）が含まれる場合、**`apply` を実行せず**、以下を行う。

- 意図した変更とドリフトを区別して、ドリフトの内容（対象リソース・属性）をユーザーに報告する
- ユーザーからの対応方針の指示（ドリフトを解消する／コード側に追従する／保留する等）を待つ
- 指示を得たうえで、必要な対応（コード修正、または現状を許容したうえでの `apply` 実行）を行う

**ユーザーの承認が不要なのは、意図した変更のみを含む `apply` に限る**。ドリフトを含む `apply` は、
常にユーザーの指示を得てから実行する。

## 4. plan ログ・出力戦略

- plan のフル出力はログファイルに保存する
- AI は stdout から Plan サマリーと変更内容を抽出してユーザーに提示する
- 詳細な確認が必要な場合のみ、保存済みログを Read ツールで読む（トークン節約）

## 5. 設定・構成ルール

- `.tfstate` はリモート（S3 等）で管理する。ローカルに残さない
- バックエンド設定・変数ファイルは環境ごとに分離する
- IAM リソースは `iam-*.tf` に関心事ごとに分割する
- **tf ファイルはリソース自体のサービス単位で分割する**: 各リソースは「何の機能のために使うか」ではなく
  「そのリソース自体がどのサービスか」で管理ファイルを決める。例えば EventBridge リソースは
  `eventbridge.tf`、CloudWatch アラームは `cloudwatch.tf`、S3 バケットとその関連リソース
  （暗号化・パブリックアクセスブロック・オブジェクト所有者・ライフサイクル・アクセスログ等）は
  用途を問わず `s3.tf` に追記する。呼び出し元の機能単位ファイル（例: `waf.tf`）には、
  他サービスのリソースを参照する設定（例: `aws_wafv2_web_acl_logging_configuration` から
  S3 バケットを参照）のみを置き、参照先リソース自体は置かない。
  新規サービスの場合のみ新しい `.tf` ファイルを作成する
- 機密値を含む変数の扱いは [security.md](security.md) に従う

## 6. 環境ごとの適用方針

- **検証・ステージング環境**: ローカルからの `plan` / `apply` を許可する
- **本番環境**: PR を `main` にマージ後、CI/CD が自動で適用する。
  **ローカルからの本番 `plan` / `apply` は行わない**
- **単一環境で CI/CD がある場合（例: `infra-oci`）**: 検証・ステージング環境を持たないため、
  ローカルでの `plan` は内容確認のみに使う。`apply` は本番環境のみが存在し、
  常に CI/CD（PR で `plan`、`main` マージで `apply`）経由で行う。ローカルからの `apply` は行わない
- **例外（CI/CD・ステージング環境を持たない個人開発基盤）**: 環境が単一で
  CI/CD が存在しないため、ローカルから `plan` / `apply` を行う。作業順序は3章に従い、
  ドリフトがなければユーザーの承認を待たずに `apply` する（ドリフトがある場合は3.1節に従う）

## 7. CI 確認（PR 作成後）

PR 作成後の CI 監視・結果提示・マージ承認の流れは [git-workflow.md](git-workflow.md) 9章に従う。
Terraform 固有の確認観点は以下のとおり。

- CI の `Plan: X to add, Y to change, Z to destroy` の件数
- 変更されるリソース一覧（`will be updated/created/destroyed` の行）
- **属性（パラメータ）単位の差分確認**: 各リソースの diff に含まれる `+`/`-`/`~` 行を1行ずつ照合し、
  今回のコード変更で意図した属性のみが変化しているかを検証する。コード変更前から本番実態とコードが
  ズレていたドリフト等、意図していない属性変更が含まれる場合は見落とさずユーザーに明示的に報告する
- ステージングとの plan 件数差分（差分がある場合はその理由も説明する）

## 8. Apply 確認（マージ後）

マージ後に自動で本番 apply が走る構成の場合、AI はその CI の完了も監視し、実行 URL と結果を
ユーザーに報告する（[git-workflow.md](git-workflow.md) 9.3 に従う）。
apply 結果がステージングと同件数であることを確認する。

## 9. 破壊的変更を含む PR の扱い

マージが即座に本番 apply を引き起こす構成では、削除（`destroy`）を含む PR を承認待ちのまま
開いたままにしない。plan 内容の確認が終わったら、マージするか一旦クローズするかを必ず決着させる。

## 10. 標準スクリプト

plan / apply / SSH 接続は、`~/.claude/scripts/` の共通スクリプトを使う
（[shell-operations.md](shell-operations.md) 4章）。リポジトリルートから実行し、
リポジトリ内にラッパースクリプトを複製しない。

| スクリプト | 内容 |
| --- | --- |
| `tf_plan.sh` | `fmt` → `init` → `validate` → `plan` を実行し、実行計画を `$TF_DIR/tfplan`、フル出力を `$TF_DIR/tfplan.log` に保存する。標準出力は Plan サマリーと変更内容のみ |
| `tf_apply.sh` | `$TF_DIR/tfplan` を適用し、適用後に実行計画を削除する。計画ファイルが無い場合は中断する |
| `tf_ssh_connect.sh` | `terraform output` から接続先 IP・ユーザーを解決して SSH 接続する（ユーザー実行用） |

- 既定は `TF_DIR=terraform`。環境ごとに引数が必要な場合は環境変数で渡す
  （`TF_INIT_ARGS`: `init` への追加引数、`TF_PLAN_ARGS`: `plan` への追加引数。
  `tf_ssh_connect.sh` は `TF_OUTPUT_IP` / `TF_OUTPUT_USER` で output 名を変更できる）
- リポジトリ固有の値（output 名・変数ファイル名等）を持つ処理が必要な場合のみ、
  そのリポジトリの `scripts/` に個別スクリプトを置く
