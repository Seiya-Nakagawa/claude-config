# Git 運用ルール（PR ベース）

全リポジトリ共通の Git 運用ルール。**すべての変更は Pull Request 経由で `main` に入れる。**
プロジェクト個別の規約でこのルールを緩めてはならない。

## 1. 基本原則

- ブランチ戦略は **GitHub Flow** を採用する
- **`main` への直接コミット・直接プッシュを禁止**する（ドキュメントのみの変更であっても例外としない）
- 変更は必ず作業ブランチで行い、PR を作成してマージする
- **対応を開始する際は Issue を作成する**。ただし事前調査・情報収集のみの段階では不要とし、
  作業ブランチを作成して対応に着手する直前に作成する
- **AI は Issue 作成・ブランチ作成・コミット・プッシュ・PR 作成までを自動で実施する**。
  都度ユーザーの許可を求めない。ただし、**CI の起動契機となるコード変更は、
  デプロイ先環境での動作確認が完了してからコミット・プッシュする**（リリース方針。第12章）
- **Issue の起票は、ユーザーの確認を待たず AI が自動で行う**。Issue はコードにも環境にも影響を
  与えず、不要であればクローズすればよい可逆操作であるため、承認を求める対象としない。
  作業中に見つけた別件の課題・改善点・技術的負債についても、その場で「Issue にしますか」と
  問わずに起票し、**起票後に Issue 番号・タイトル・URL をユーザーへ報告する**。
  ラベルが存在しない場合は `gh label create` で作成してから付与する（第5章）。
  ただし Milestone・Project の新規作成は対象外とし、第8章に従い事前にユーザーの了承を得る
- **ユーザーのレビューは PR 上で行う**。AI は PR の URL と変更概要を提示して判断を仰ぐ
- リポジトリに CI（ビルド・テスト・IaC の plan 等）が設定されている場合、PR 作成後の CI 監視・結果確認も
  AI が自動で行う。ユーザーの「CI 完了」報告を待たない（第9章参照）
- マージの実行可否はユーザーが判断する。**ユーザーから明示的な承認（マージ指示）を得た場合に限り、AI がマージを実行してよい**。
  承認なくAIが独断でマージしない

## 2. 作業フロー

1. 対応内容を Issue として作成する（事前調査・情報収集のみの段階では不要。
   実際に対応へ着手する直前、すなわち作業ブランチを作成する前に行う）。
   Milestone・Project は、大きな対応でタスク管理が必要な場合のみ設定する。
   単発タスクでは設定しない（第8章参照）

   ```bash
   gh issue create --title "{内容}" --body "{概要}"
   ```

2. `main` を最新化する

   ```bash
   git switch main && git pull origin main
   ```

3. 作業ブランチを作成する

   ```bash
   git switch -c {prefix}/{内容}
   ```

4. 変更を実施する
5. デプロイ先環境（ローカル・ステージング）へデプロイし、動作確認を行う。
   動作確認の結果をユーザーに報告する（第12章。ドキュメントのみの変更など、
   デプロイ対象がない場合はこの手順を省略する）
6. コミットする（メッセージは第4章を参照）。CI の起動契機となるコード変更は、
   動作確認の完了後に行う
7. 作業ブランチをプッシュする

   ```bash
   git push -u origin {ブランチ名}
   ```

8. PR を作成する（第5章を参照）。Issue を作成済みの場合は PR 本文に `Closes #{Issue番号}` を含め、
   マージ時に Issue が自動クローズされるようにする
9. **PR の URL と変更概要をユーザーに提示する**。リポジトリに CI が設定されている場合は、
   ユーザーの報告を待たず AI が CI の監視・結果確認まで行う（第9章参照）。
   その上でレビュー・マージ承認を待つ
10. マージ後、ローカルおよびリモートの作業ブランチを削除する

   ```bash
   git switch main && git pull origin main
   git branch -d {ブランチ名}
   git push origin --delete {ブランチ名}
   ```

## 3. ブランチ命名

`{prefix}/{内容}` の形式とし、目的と内容が分かる名前にする。

| prefix | 用途 |
| ------ | ---- |
| `feature/` | 新機能の追加 |
| `fix/` | バグ修正 |
| `docs/` | ドキュメントのみの変更 |
| `refactor/` | 動作を変えないコードの修正 |
| `chore/` | ビルド・補助ツール・設定の変更 |

- Issue を作成した場合は `{prefix}/issue-{番号}-{内容}` の形式とする（例: `feature/issue-123-login-form`）
- 事前調査段階のみで Issue を作成していない場合は内容のみで可（例: `docs/oci-migration-requirements`）

## 4. コミットメッセージ

- **Conventional Commits** に従い、先頭に Type を付ける
- Type は `feat` / `fix` / `docs` / `style` / `refactor` / `test` / `chore` を使用する
- Type 以外のタイトル・本文は日本語で記述する（英語の方が分かりやすい単語は英語のままで可）
- 1行目は変更内容の要約とし、詳細は本文に記述する
- 例: `docs: デプロイ手順のドキュメントを更新`

## 5. Pull Request

- PR は `gh pr create` で作成する
- **タイトル・本文は日本語**で記述する
- 本文には以下を含める

  ```markdown
  ## 概要

  何を、なぜ変更したか。

  ## 変更内容

  - 変更点を箇条書きで列挙する

  ## 確認事項

  - レビュー時に確認してほしい点、判断を仰ぎたい点
  ```

- 未解決の論点や、AI が仮定を置いて進めた箇所は「確認事項」に明記する
- **変更種別に応じたラベルを付与する**（`--label`）。標準ラベルは以下のとおり。
  リポジトリに存在しない場合は `gh label create` で作成してから付与する。
  複数の種別にまたがる場合は複数付与してよい
  - `terraform`: Terraform 等の IaC の変更
  - `gas`: Google Apps Script の変更
  - `lambda`: Lambda アプリケーションの変更
  - `docs`: ドキュメントのみの変更
- PR 作成後は、PR の URL と変更概要をユーザーに提示する

### 5.1. PR 作成のタイミング

プッシュ・PR 作成にユーザーの許可は不要である。ただし、プッシュ・PR 作成が CI（ドライラン等）の
起動契機となるため、**CI を起動するコード変更は、デプロイ先環境での動作確認が完了してから**
コミット・プッシュ・PR 作成を行う（第12章）。動作確認前の未確認のコードを CI に流さない。

- ドキュメントのみの変更など、デプロイ対象がない変更は、動作確認を待たずに PR を作成してよい
- 設計書を先にレビューする場合（[docs-sync.md](docs-sync.md) 1章）の設計書のみの PR も、
  動作確認を待たずに作成してよい

## 6. 禁止事項

- `main` への直接プッシュ
- **ユーザーの明示的な承認を得ずに** AI が PR をマージすること
- `git push --force` / `--force-with-lease`（ユーザーが明示的に指示した場合のみ許可する）
- コミット済み履歴の書き換え（`rebase`、`commit --amend`）をユーザーの指示なく行うこと

`main` への直接 push と force push は、PreToolUse hook（`scripts/block-protected-git-push.sh`）で
機械的にブロックしている。ユーザーの指示で force push が必要な場合は、ユーザー自身に
`! git push --force ...` での実行を依頼する。

## 7. `.claude` 配下の変更

- プロジェクト配下の `.claude/` に変更がある場合は、対応中の作業ブランチに含めてコミットする
- ホームディレクトリ配下のグローバル設定（`~/.claude/`）は、それ自体が Git リポジトリ
  （公開リポジトリ）である。規約・スキル・エージェント・共通スクリプトを変更する場合は、
  対応中の他リポジトリの作業とは別に、`~/.claude` 側で本規約の作業フロー（Issue 〜 PR）に従う。
  コマンドは `git -C ~/.claude` で実行する
- 公開リポジトリのため、`~/.claude/` の管理対象に接続先ホスト・アカウント ID 等の環境固有の情報や
  機密情報を書かない（プロジェクト個別の `CLAUDE.md` やメモリに置く）
- `~/.claude/settings.json` も管理対象である。Claude Code 自身による書き換えも含むため、コミット前に差分を確認し、
  機密情報や IP アドレスが混入していないことを確かめる（SSH 接続先は `~/.ssh/config` のホスト別名で指定する）

## 8. Milestone によるフェーズ管理

**Milestone・Project は、大きな対応でタスク管理が必要になった場合のみ作成・設定する**（作成時は事前にユーザーの了承を得る）。
単発タスクの Issue には設定しない。フェーズの定義・命名（`NN.フェーズ名`）・運用手順は
[feature-flow スキルの GitHub 運用リファレンス](../skills/feature-flow/github-reference.md#8-milestone-によるフェーズ管理)に従う。

## 9. CI/CD 監視・承認フロー

PR 作成後、当該リポジトリに CI（ビルド・テスト・Terraform 等 IaC の plan 実行等）が設定されている
場合は、以下の流れに従う。ユーザーの「CI 完了しました」等の報告を待たず、AI が自ら監視・確認まで
一気通貫で行う。リポジトリに CI が設定されていない場合は、本章の監視フローは適用しない
（ただしマージ前のユーザー承認は12章に従い必須とする）。
PR 作成に至るまでの流れ（デプロイ・動作確認）は12章に従う。

### 9.1. CI 実行の監視

- PR 作成後、CI の実行を待たず放置しない。`gh pr checks {PR番号} --watch` や `gh run watch` 等で
  完了まで監視する
- CI の実行 URL を取得し、必ずテキストメッセージでユーザーに提示する（コマンド出力に埋もれさせない）

### 9.2. 結果の抽出・提示

- CI のログ全文をそのまま貼り付けず、意味のある要約を抽出して提示する
  - IaC の plan の場合: 追加・変更・削除の件数サマリーと、変更されるリソースの一覧を提示する。
    さらに `+`/`-`/`~` の属性単位の差分を照合し、今回のコード変更で意図した属性のみが変化しているかを
    検証する。コード変更前から実態とコードがズレていたドリフト等、意図しない変更が含まれる場合は
    見落とさず必ずユーザーに明示する
  - テスト・ビルドの場合: 成功・失敗件数、失敗時は失敗内容と原因箇所
- 詳細な確認が必要な場合は、ログをファイルに保存し Read ツールで読む（コンテキスト節約のため、
  長大なログをそのまま出力しない）

### 9.3. 承認と実行

- CI 結果の提示後、マージ・本番適用（apply/deploy）等のさらなる不可逆操作は、
  ユーザーから明示的な承認を得てから AI が実行する（1章の原則に従う）
- 承認を得たら、AI がマージを直接実行する

  ```bash
  gh pr merge {PR番号} --squash --delete-branch
  ```

  `--delete-branch` により、`main` への切替・pull・ローカルブランチ削除・リモートブランチ削除が
  自動実行される

- マージ後に自動で本番反映（apply/deploy）が走る CI/CD 構成の場合、AI はその CI の完了も同様に
  監視し、結果をユーザーに報告する。ユーザーが別途 URL を確認しに行く必要がないようにする

## 10. GitHub Project（プロジェクトボード）の運用

Issue クローズ時に、対応する Project の全アイテムが完了していれば AI が自動でクローズしてよい。手順は
[GitHub 運用リファレンス](../skills/feature-flow/github-reference.md#10-github-projectプロジェクトボードの運用)に従う。

## 11. GitHub CLI（`gh`）利用時の注意点

- `gh issue view` は `--json` で必要なフィールドを指定する
- `gh pr create` はヒアドキュメント展開形式（`--body "$(cat <<'EOF' ... EOF)"`）を使い、`mktemp` + `--body-file` は使わない
- 詳細・コマンド例は [GitHub 運用リファレンス](../skills/feature-flow/github-reference.md#11-github-cligh利用時の注意点)を参照する

## 12. リリース方針（標準フロー）

全リポジトリ共通のリリースの流れ。**「先にデプロイ先環境で動作確認を済ませ、確認済みのコード変更のみを
コミット・プッシュして PR・CI・CD に流す」** ことを原則とする。

### 12.1. 標準フロー

| 手順 | 内容 | 担当 |
| --- | --- | --- |
| 1 | コード修正 | AI |
| 2 | ローカルまたはステージング環境へデプロイ（12.2節） | AI |
| 3 | デプロイした環境での動作確認 | AI |
| 4 | 動作確認の結果をユーザーに報告する。ユーザー自身の確認が必要な対象（GAS 等）は、依頼して確認完了を待つ | AI → ユーザー |
| 5 | 動作確認の完了後、コミット・プッシュ・PR 作成を行う（ユーザーの許可は不要）。PR オープンをトリガーに GitHub Actions で CI、またはドライランを実行する（ドライランが可能なデプロイ対象の場合） | AI |
| 6 | CI の結果に問題がなければ、結果を提示し**マージの許可を得る** | AI → ユーザー |
| 7 | **ユーザーの許可を得たらマージ**し、マージをトリガーに GitHub Actions で CD を実行する。CD の結果を監視して報告する | AI |

- 動作確認前は、CI の起動契機となるコード変更をコミット・プッシュしない
  （ドキュメントのみの変更等は、動作確認を待たずに PR にしてよい）
- ユーザーの許可が必要なのは手順6のマージのみである（ユーザー自身の確認が必要な対象の動作確認を除く）
- 手順5以降の CI の監視・結果提示・マージ・CD の監視の詳細は、9章に従う
- CI で問題が検出された場合、または追加の修正が必要になった場合は手順1へ戻る。
  デプロイ済みの挙動に影響する修正を加えたときは、手順2〜4（再デプロイ・再確認）をやり直す

### 12.2. プロジェクトごとの違い

手順2のデプロイ先、手順5の CI / ドライランの有無、手順7の CD の有無はプロジェクト・対象により異なる。
具体的な値は各リポジトリの `CLAUDE.md` に従い、以下を基準とする。

| 対象 | 手順2 のデプロイ先 | 手順5 の CI | 手順7 の CD |
| --- | --- | --- | --- |
| Terraform（ステージング環境あり） | ステージングへ `plan` / `apply` | `plan`（ドライラン） | 本番へ `apply` |
| Terraform（環境が単一で CI/CD あり） | なし（ステージングが無いため、事前の動作確認は PR 上の `plan` 差分確認に限る。[terraform.md](terraform.md) 6章） | `plan`（ドライラン） | 本番へ `apply` |
| Terraform（環境が単一で CI/CD なし） | 対象環境へ `plan` / `apply`（[terraform.md](terraform.md) 6章） | なし | なし |
| Lambda | 検証環境の関数コードを更新 | テスト・ビルド | 本番の関数コードを更新 |
| GAS | 既存デプロイを更新（[gas-deploy-flow.md](gas-deploy-flow.md)）。CI/CD で自動デプロイするスクリプトは gas-deploy-flow.md 5章に従い、事前デプロイなし | 設定がある場合のみ | 設定がある場合のみ（gas-deploy-flow.md 5章） |
| ドキュメントのみ | なし（手順2〜4を省略） | 設定がある場合のみ | なし |

- CI / CD が存在しない対象では、手順5の CI 監視・手順7の CD 監視を省略する。
  ただし手順6のマージ承認は必須とする
- 本番環境へのデプロイは、常にマージ後の CD で行う。ローカルから本番へ直接デプロイしない
