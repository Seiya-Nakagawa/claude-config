# ドキュメント同期ルール

## 1. 作業前の設計書確認

- **コード修正（IaC・GAS・アプリケーション等の種別を問わず）に着手する前に、必ず関連する設計書を
  確認する**
- **設計書を先に更新してからコード修正に着手する**: 今回の変更が設計書に記載された方針・構成と
  乖離する、または設計書に記載のない新規要素を追加する場合は、**まず設計書を更新**する
  （必要に応じてユーザーの確認を得る）
- **原則、設計書の更新後はユーザー確認を挟まず、そのまま同一の Issue・ブランチ・PR で
  コード修正（実装）に進む**: 設計書とコードは同一 PR に含め、レビューは PR 上で行う
- **次の場合のみ、設計書更新後にユーザーの明示的な承認を得てからコード修正に進む**
  - 設計と実装を**別 Issue** で管理している場合（設計の Issue・PR を先にレビュー・マージする）
  - **大規模な改修**の場合（複数コンポーネントにまたがる、構成・方式の根本的な変更、
    データ移行や不可逆な操作を伴う等）
- 承認を得る場合は、設計書の変更をコミット（`docs:` プレフィックス）してプッシュしたうえで
  PR を作成する（PR が未作成の場合は新規作成、既存 PR がある場合は追加コミットのプッシュのみでよい）。
  PR の URL を提示してレビューを依頼し、**明示的な承認を得るまでコード修正に着手しない**
- 着手順序は、原則「**設計書更新 → コード修正**」、承認が必要な場合は
  「**設計書更新 → プッシュ・PR 作成・レビュー依頼 → ユーザー承認 → コード修正**」とする。
  設計書の方針に対してユーザーから修正・停止の指示があった場合はそれに従う
- 設計書の格納場所・章立て・記述形式は [document-standards.md](document-standards.md) に従う

## 2. コード変更時のドキュメント更新

コードを変更する際は、必ず `docs/` 以下のドキュメントも同時に更新すること。

- 設計書の方針・構成に影響する変更は、1章に従い設計書を先に更新する
- リポジトリ全体の概要（ルート `README.md`）、コンポーネント個別の `README.md` は、
  構成・トリガー・環境変数・依存関係に変更があった場合に同一 PR 内で更新する

## 3. ドキュメント修正時のフロー

ドキュメントのみの変更であっても `main` へ直接プッシュしない。
[git-workflow.md](git-workflow.md) の作業フロー（Issue 作成 〜 PR 作成）にそのまま従う。
ドキュメント固有の点のみ以下のとおりとする。

- 作業ブランチは `docs/` プレフィックスを使用する
- コミットメッセージの Type は `docs` を使用する
- PR には `docs` 相当のラベルを付与する

## 4. 構築フェーズの Issue 対応

Milestone「03.構築」（[git-workflow.md](git-workflow.md) 8章）に属する Issue でコードを変更する場合、
実施した手順を [document-standards.md](document-standards.md) 2.4節・3.4節の構築手順書として
`docs/04.build/` 配下に必ず記録し、コード変更と同一 PR に含める。
